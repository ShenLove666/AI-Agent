# 商家 AI 助手产品运营闭环设计

日期：2026-08-07
状态：已完成对话评审，待用户审阅书面版本

## 1. 背景与目标

当前项目是在 `D:\Project\ragent-main` 基础上改造的 Python/FastAPI 版本，已经具备知识库、RAG 对话、ConversationTurn、答案版本、引用、反馈、Trace 和部分运营指标，但参考项目中的 Agent、MCP、意图树、知识图谱、入库 Pipeline、评测等能力尚未全部实现，部分前端页面也缺少真实后端闭环。

本阶段不追求逐页复刻参考项目，而是面向“AI 产品运营实习生”岗位，建设一条可真实演示、可解释、可回归验证的商家 AI 助手落地闭环：

```text
公开电商资料 + 模拟商家数据
        ↓
知识库入库与质量检查
        ↓
商家 AI 助手问答
        ↓
引用、反馈与失败诊断
        ↓
评测集与答案版本对比
        ↓
运营洞察与优化建议
```

## 2. 产品原则

- 求职展示优先：每项能力都能映射到需求调研、产品落地、Agent 质量优化或数据运营。
- 少而完整：只开放具有真实后端能力、真实状态和自动化测试的功能。
- 证据可追溯：指标、诊断和评测结果必须能下钻到回答、引用、答案版本或 Trace。
- 数据诚实：模拟数据明确标记为“演示数据”，不得冒充真实线上业务指标。
- 本地开箱即用：默认使用 SQLite、本地文件和可选 LLM API，不强制依赖 Redis、Milvus 或云服务。
- 保留演进空间：Agent、MCP、图谱和意图树保留为后续阶段，但不进入本阶段验收范围。

## 3. 第一阶段产品范围

### 3.1 商家 AI 助手

- 多轮对话和 ConversationTurn 状态一致性。
- 知识库范围选择和 Turn Scope Snapshot。
- 深度思考、主动停止、失败恢复和明确的流式错误。
- 同一 Turn 的重新生成、答案版本切换和具体版本反馈。
- 引用来源、知识命中和 Trace 下钻。

### 3.2 知识运营

- 知识库、文档和 Chunk 的真实 CRUD。
- 公开资料和模拟商家资料导入。
- 文档解析、切块预览、入库进度、失败原因和重试。
- 索引完成状态和知识质量检查。
- 只有完成索引的文档能够参与检索。

### 3.3 商家反馈闭环

- 点赞、点踩和可选的问题标签。
- 将负反馈、知识未命中、生成失败和慢响应转入待优化问题池。
- 支持问题状态、负责人备注、处理记录和证据关联。

### 3.4 RAG 评测中心

- 评测数据集、案例、实验运行和运行结果。
- 确定性评测与可选 LLM Judge。
- 检索、回答、引用、拒答和性能指标。
- 实验或答案版本之间的对比与失败案例下钻。

### 3.5 AI 产品运营驾驶舱

- 工具渗透率、回答成功率、知识命中率、反馈覆盖率和好评率。
- 高频业务问题、主要失败原因、待处理问题和优化效果趋势。
- 所有指标从真实数据库聚合，不返回硬编码统计数字。

### 3.6 演示数据中心

- 一键创建演示管理员、普通商家、知识库、文档、历史对话、反馈、问题和评测集。
- 一键清理并可重复生成，结果在相同随机种子下可复现。
- 演示数据和用户自行创建的数据通过明确字段或独立演示租户区分。

## 4. 不在本阶段范围内

- 完整 Agent 编排和工具调用平台。
- MCP Server 管理界面。
- 知识图谱构建和图检索。
- 树形意图配置后台。
- 分布式任务队列和多节点部署。
- 参考项目所有管理页面的逐页复刻。

上述功能不得通过假接口、静态数据或可直达的半成品页面伪装为已完成。

## 5. 信息架构与前端设计

主导航收敛为：

```text
AI 助手
知识运营
评测中心
问题诊断
运营洞察
系统设置
```

### 5.1 视觉方向

- 延续蓝白品牌基调，形成专业 B2B AI 工作台。
- 建立统一的颜色、排版、间距、圆角、阴影、状态色和图表色板。
- 减少页面级 Hex 硬编码，使用设计 Token 和共享组件。
- 风险、待处理和增长机会使用少量暖色突出。
- 桌面端优先，保证常见笔记本分辨率下布局不溢出。

### 5.2 交互要求

- 所有页面具备加载、空数据、失败、无权限和演示数据状态。
- 运营指标可以下钻到问题、反馈、回答版本或 Trace。
- 文档预览和重型管理页面按需加载。
- 不展示没有真实后端实现的操作按钮和入口。
- 用户能够独立完成“发现问题—查看证据—执行优化—验证效果”。

## 6. 数据策略

### 6.1 公开资料

公开数据覆盖电商售后、物流、商品发布、消费者权益等主题。每份资料保存：

- 来源 URL；
- 来源机构或站点；
- 获取日期；
- 内容摘要；
- 授权或使用说明；
- 是否为原文、摘要或结构化改写。

不将受限制的完整版权内容直接打包进仓库。

### 6.2 模拟数据

模拟数据包括虚构店铺规则、客服 SOP、用户问题、答案反馈、失败类型、使用频次和处理记录。所有记录具有 `is_demo` 或等价标识，界面统一展示“演示数据”。

### 6.3 评测数据

每条评测案例至少包含：

- 问题；
- 业务分类和难度；
- 知识库范围；
- 期望关键点；
- 期望引用文档；
- 是否应该拒答；
- 可选参考答案。

## 7. 后端架构

后端保持 FastAPI 模块化单体：

```text
app/modules/
├─ conversations   # Turn、答案版本和上下文状态
├─ knowledge       # 文档、Chunk、索引版本和质量状态
├─ ingestion       # 可恢复入库任务和节点日志
├─ retrieval       # Scope、关键词/向量、融合和重排
├─ rag             # 改写、Prompt、生成和 Trace
├─ feedback        # 反馈、问题标签和诊断工作流
├─ evaluation      # 数据集、实验、指标和失败案例
└─ operations      # 运营指标聚合和趋势
```

各模块通过服务接口和数据库实体协作，不直接依赖其他模块的 HTTP DTO。普通 JSON API、文件下载、204 和 SSE 使用明确且独立的协议约定。

## 8. 核心数据流

### 8.1 在线问答

```text
创建或恢复 ConversationTurn
 → 固化知识范围和模型开关
 → 构建 active completed turns 上下文
 → 查询改写
 → 多路检索
 → 融合与可降级重排
 → 生成带引用答案
 → 保存答案版本、Trace 和反馈入口
```

### 8.2 问题诊断

```text
反馈/失败/低分评测
 → 自动归因候选
 → 运营人员确认
 → 关联知识或策略改动
 → 重新评测
 → 验证通过后关闭
```

诊断状态为：`new → confirmed → optimizing → pending_verification → resolved`。

### 8.3 演示初始化

```text
seed-demo
 ├─ 创建演示用户
 ├─ 创建知识库
 ├─ 导入并索引资料
 ├─ 创建历史问答和反馈
 ├─ 创建问题诊断记录
 ├─ 创建标准评测集
 └─ 生成可复现的运营指标输入
```

## 9. 评测设计

### 9.1 检索指标

- Recall@K；
- MRR；
- 引用文档命中率；
- 知识范围正确率；
- 无结果率；
- 检索故障率。

### 9.2 回答指标

- 关键点覆盖率；
- 引用完整性；
- 忠实度或幻觉风险；
- 拒答正确率；
- 首 Token 时间和总耗时；
- 用户反馈率与好评率。

### 9.3 评分方式

- 确定性评测默认启用，不依赖额外模型。
- LLM Judge 是可选增强能力，保存评分、理由、模型和 Prompt 版本。
- 综合分必须保留子指标，不能掩盖失败原因。
- 评测运行必须记录配置快照，以保证实验可比较和可复现。

## 10. 可靠性与安全

- 文档只有在索引成功后参与所有检索通道。
- 入库任务持久化并支持超时回收、有限重试和节点日志。
- 全通道故障返回检索不可用；正常零结果返回无相关资料。
- Reranker 异常或分数数量不匹配时回退融合结果。
- RequestRun 使用租约或等价的过期抢占语义，避免永久 processing。
- 新增数据库结构使用 Alembic，提供空库升级和现有 SQLite 升级测试。
- 普通用户只能访问自己的会话、知识库和文档；管理功能要求管理员权限。
- 默认 JWT 密钥只能用于开发环境；生产模式必须提供强密钥。
- 日志、Trace 和评测记录不得保存 API Key，Prompt 保存支持脱敏策略。

## 11. 错误处理

- 前端 Axios 与 SSE 统一转换为 `ApiError`，保留 status、code、details、traceId 和 messageId。
- 用户可恢复错误提供明确操作，例如重试入库、重新生成或重新运行评测。
- 外部模型不可用时，历史数据、知识库、评测结果和后台统计仍可浏览。
- UI 不将“没有数据”“没有命中”“服务故障”和“无权限”混为同一空状态。
- 后台任务和评测运行失败保留错误摘要、节点状态和 Trace，不静默吞错。

## 12. 测试策略

### 12.1 后端

- 权限和多租户隔离；
- 入库任务恢复和索引状态；
- 检索降级与零结果语义；
- ConversationTurn、答案版本和上下文；
- 评测指标和运营聚合；
- Alembic 空库及旧库升级。

### 12.2 API 契约

- 从前端 Service 和 FastAPI OpenAPI 对比路径、方法和核心 DTO。
- 已启用页面不得出现未知 404 或未处理的字段漂移。

### 12.3 前端

- 使用 Vitest 与 Testing Library 覆盖聊天状态、版本切换、诊断状态和评测筛选。
- TypeScript、ESLint 和生产构建进入统一验证命令。

### 12.4 E2E

使用 Playwright 覆盖：登录、初始化演示数据、导入知识、提问、反馈、问题诊断、重新评测和指标变化。

## 13. 交付阶段

1. 基础治理：补充项目上下文、Alembic、API 契约和演示数据框架。
2. 知识运营闭环：可靠入库、索引状态、知识质量和公开资料。
3. 反馈与诊断闭环：问题池、自动归因、处理状态和 Trace 下钻。
4. RAG 评测中心：数据集、运行、指标、失败案例和版本对比。
5. 运营驾驶舱：真实聚合指标和优化前后趋势。
6. 前端统一改造：设计 Token、核心页面、响应状态和按需加载。
7. 最终验收：全量测试、E2E、README、演示脚本和简历描述。

每个阶段必须形成独立 OpenSpec change，完成测试和验收后再进入下一阶段，避免一个超大变更无法审查或回滚。

## 14. 完成标准

- 一条明确命令可以生成可重复的本地演示环境。
- 核心链路刷新页面后状态仍一致。
- 所有开放页面均使用真实 API 和数据库状态。
- 所有关键指标能够下钻到原始证据。
- 后端测试、API 契约、前端测试、Lint、构建和关键 E2E 全部通过。
- README、系统行为、演示脚本和简历描述一致。
- 无模型 API 时项目仍可浏览演示数据和已有评测结果；需要模型的操作明确提示配置要求。

## 15. 首个实施变更

首个 OpenSpec change 聚焦“演示与评测基础治理”，范围限定为：

- 建立正式 Alembic baseline 和升级测试；
- 建立可重复的演示数据模型、命令和清理机制；
- 建立公开资料元数据规范；
- 建立评测数据集与案例的最小数据模型；
- 建立前端 Service 与 OpenAPI 的契约基线；
- 补充统一验证入口。

该变更不包含完整评测执行器、运营驾驶舱重做或全部页面视觉改造，以保证首个计划可独立完成和验收。
